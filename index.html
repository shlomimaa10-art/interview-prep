🗃 Database Systems — Interview Cheatsheet

Click any topic → Study mode
SQL
PostgreSQL / MySQL
B-Tree (InnoDB) / heap+MVCC (Postgres). WAL for crash recovery; MVCC for concurrent reads. NOT built-in → Vitess (MySQL) or Citus (Postgres). Cross-shard txns need 2PC — expensive, often avoided. CAP: CP → refuses writes under partition.
Cassandra
Storage: LSM-Tree → MemTable(RAM) → SSTable(disk, immutable). Index: partition key only (consistent hash ring). Secondary indexes expensive — model data around queries. Sharding: consistent hashing; vnodes → add node moves ~1/N keys. CAP: AP by default; tunable per-query (ONE/QUORUM/ALL).
NoSQL
MongoDB
WiredTiger (B-Tree underneath) — same as MySQL. Model: document (BSON) → flexible schema, no joins needed. ACID: single-doc always; multi-doc txns since v4. Sharding: native → range or hash shard key; config server tracks chunks; mongos router directs queries. CAP: tunable → CP default, AP with lower write concern.
Cosmos DB
Index: inverted index on ALL fields by default. Multi-model: SQL, Mongo, Cassandra, Gremlin, Table APIs. Sharding: automatic on partition key; global distribution. CAP: 5 consistency levels per request (Strong→Eventual). Azure Table Storage: KV; PartitionKey+RowKey; auto-sharded.
DynamoDB
KV + document; partition key → consistent hash. Secondary indexes: GSI (eventually consistent), LSI (strongly). CAP: AP default; strongly consistent reads opt-in per request.
OLAP / Analytics
Snowflake
Column store; micro-partitions (~16MB compressed). Index: NONE → metadata pruning skips irrelevant partitions. Separates storage (S3) from compute (virtual warehouses).
Kusto / ADX
Storage: each column stored+compressed separately. Index: inverted index per column (term→row bitmap). Fast WHERE col CONTAINS 'x' without scanning all rows. No B-Tree; built for log/telemetry pattern queries.
ClickHouse
MergeTree (LSM-inspired) — data sorted by primary key. Sparse primary index (1 entry/~8K rows) vs B-Tree's 1/row. Distributed table engine routes queries to shards. SQL syntax; extreme col compression; real-time OLAP.
Azure Synapse
Clustered columnstore; MPP: 60 hash-distributed nodes.
RocksDB
Pure LSM: write→MemTable→L0 SSTables→Lmax via compaction. Bloom filter per SSTable — skip disk I/O for absent keys. Write amp high (compaction rewrites); read amp medium. Embedded KV only — no server, no sharding; host DB manages. Powers: MyRocks (MySQL), TiKV (TiDB), Cassandra storage.
Storage Engines
B-Tree
Pages (4–16KB) on disk, sorted by key. Root→leaf traversal: 3–4 I/Os for millions of rows. Writes: in-place page update + WAL (crash safety). Strengths: point reads, range scans. Weakness: random writes under high load.
LSM-Tree
Write→MemTable(RAM)→SSTable(disk, immutable). Compaction: merges SSTables, reclaims tombstones. Bloom filter: skips disk read if key absent. Strengths: sequential writes = high write throughput. Weakness: read amp (check multiple SSTables), space amp.
Column store
Each column stored contiguously, not rows. Compression: RLE/delta/dict on same-type values → 10×. Aggregations touch one column, not whole rows. Weakness: single-row random writes expensive.
Inverted index
term → sorted posting list of row IDs. Fast: col CONTAINS 'x' without scanning all rows. No efficient range scans over key order.
Sharding Patterns
Hash sharding
key → hash(key) % N → shard. Even distribution. Cannot range-scan across shards. Resharding = full reshuffle.
Range sharding
Sorted key space split into ranges per shard. Efficient range scans. Hot-key risk: monotonic keys (e.g. timestamps) funnel all writes to one shard.
Consistent hashing
Nodes on a ring; key → nearest node clockwise. Add/remove node: only ~1/N keys migrate. Vnodes: each node owns multiple ring segments → even distribution.
Hot key fix
Append random suffix → scatter across N shards, aggregate on read. Write-behind cache absorbs burst, drains to shard.
CAP & Consistency
CAP theorem
P (partition tolerance) is mandatory → real choice: C vs A. CP: refuse ops during partition (Postgres, etcd, Zookeeper). AP: always serve, may return stale (Cassandra, DynamoDB).
Tunable consistency (Cassandra)
ONE: 1 ack. Fastest; stalest. Use: logs/metrics. QUORUM: floor(N/2)+1 acks. Balanced. Use: sessions. ALL: N acks. Strongest. Use: financial ledgers. Trick: R+W > N → at least 1 replica overlaps → strong consistency from AP system (e.g. N=3, R=2, W=2).
Consistency spectrum
Linearizable > Sequential > Causal > Read-your-writes > Monotonic reads > Eventual. Cosmos DB exposes all 5 as selectable levels.
Repair mechanisms
Hinted handoff: store hint for downed replica; replay on recovery. Read repair: QUORUM finds stale replica → fixes in background. Anti-entropy: Merkle tree diff syncs without client trigger.

🔑 Connect an AI provider

To run an interview, the app needs to reach an AI model. Pick one of these:

Option A — Run a local model (free)
Start copilot-api on your machine — it serves Claude/GPT through your GitHub Copilot subscription. In a terminal:
npx copilot-api start -c -m claude-sonnet-4.6
Then keep the default provider Custom / localhost in Setup.
Option B — Paste an API key (BYO)
Switch the AI Provider in Setup to Anthropic or OpenAI and paste your key in the field that appears. Keys stay in sessionStorage — they never leave the browser.
